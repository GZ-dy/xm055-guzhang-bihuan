# 运维报告话术规则

## 总原则

- 事实优先：先使用本次输入和 `incident_context`，再使用知识库话术润色。
- 知识库只使用真实历史故障报告抽取的话术，不使用本项目、Codex 或其他 AI 工具生成的报告作为历史来源。
- 未命中真实历史案例时，允许使用通用运维专业话术兜底，只润色表达，不补造原因、时间、影响范围和恢复结果。
- 证据不足时写“待确认”或进入人工复核，不编造原因、时间、影响范围和恢复结果。
- 表述应客观、可核查，避免夸大影响或使用聊天化表述。
- 同类历史报告只提供措辞参考，不直接复制日期、人员、系统状态和处理结论。

## 推荐表达

- 通用兜底表达可使用“核实故障现象”“排查关联服务状态”“复核日志及监控指标”“完成业务功能复测”“确认系统恢复正常”等运维人员常用表述。
- 故障发现来源统一写作“用户报障”“监控告警”“巡检发现”或“值班发现”。
- 处理动作使用明确动词，例如“核查”“定位”“重启”“切换”“回滚”“扩容”“复测”“确认恢复”。
- 影响范围写清业务对象和用户感知，例如“影响相关用户访问系统”“影响接口调用成功率”。
- 恢复验证写清验证对象，例如“复测登录、查询、流程流转等关键功能后确认恢复”。
- 后续措施应落到可执行动作，例如“补充监控告警”“固化恢复验证清单”“完善同类故障处置手册”。
- 数据库相关故障应写清职责边界：多域维护组排查中间件和服务侧，可拨测数据库连通性并通知亚信维护组；数据库侧内容和处置由亚信维护组负责。

## 禁用或慎用表达

- 不写“微信群反馈”，默认改为“用户报障”，除非明确要求保留渠道。
- 不写“可能是”“大概是”“应该恢复了”等无法核查表述。
- 不把本项目生成的报告、AI 模拟报告或测试样例当作历史案例来源。
- 不用历史报告中的具体时间、人员、外部单位结论替代本次证据。
- 不把“重启后恢复”直接写成根因，除非本次证据已经确认根因。
- 不把模板示例内容当作真实故障内容。
- 不把数据库侧处置写成多域维护组负责；多域侧只写中间件、服务排查、数据库拨测和通知亚信维护组处理。

## 抽取要求

从历史报告抽取话术时，保留通用表达，删除或泛化敏感事实：

- 人员姓名改为“处理人员”或“值班人员”。
- 具体账号、IP、主机名、手机号和客户名称应删除或泛化。
- 只保留可复用的故障类型、处理逻辑、验证动作和后续措施。
