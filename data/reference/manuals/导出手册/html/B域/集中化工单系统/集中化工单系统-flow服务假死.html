适用范围与故障判定

适用范围

遇到以下任一现象，进入本手册流程处理：

  • 集中化工单系统无法登录或登录异常。
  • flow 服务假死，进程在但请求无响应或超时。
  • pod 启动后服务实例长期未就绪（readiness probe 持续失败）。
  • 多实例同时未就绪导致所有用户无法登录。

判定规则

如果看到先做什么判断结论 ------------------------------ 用户报障无法登录抓取 flow pod 状态与日志收敛到 flow 服务侧 pod Running 但 readiness 失败检查探针配置和启动依赖服务假活，先恢复探针 恢复后仍有登录失败回查页面、接口、日志和监控确认假恢复或依赖未恢复

标准处置流程

  • 记录故障时间、登录现象、影响入口和受影响实例数。
  • 抓取 flow pod 列表和状态：

```bash

kubectl -n get pod -l app=flow -o wide

```

  • 抓取未就绪实例的就绪探针日志和事件：

```bash

kubectl -n describe pod

kubectl -n logs --previous --tail=300

```

  • 确认旧实例已隔离或标记不接流量后，修改 pod 健康检查机制（存活/就绪探针），滚动重启。
  • 重启后验证用户登录和集中化工单系统核心入口。
  • 恢复后保留现场（探针配置 diff、pod 事件、关键日志），便于根因回溯。
  • 短时间复发时升级开发定位根因，并补充进程级和就绪级监控。

关键检查命令

以下命令按本故障场景去重整理；执行前按实际命名空间、标签和权限确认。

列出 flow pod 状态


kubectl -n <ns> get pod -l app=flow -o wide

查看未就绪 pod 详情


kubectl -n <ns> describe pod <pod>

抓取 flow 最近日志


kubectl -n <ns> logs -l app=flow --tail=300 --since=30m

查看 readiness/liveness 探针配置


kubectl -n <ns> get pod <pod> -o jsonpath='{.spec.containers[*].livenessProbe}'
kubectl -n <ns> get pod <pod> -o jsonpath='{.spec.containers[*].readinessProbe}'

滚动重启 flow


kubectl -n <ns> rollout restart deployment/flow
kubectl -n <ns> rollout status deployment/flow

协同分工与通知口径

通知口径

集中化工单系统出现 flow 服务假死，当前已按手册确认主故障对象为 flow pod 健康检查机制。请对应责任团队优先处理主故障点，运维侧同步保留现场并完成登录、业务入口和监控恢复验证。

恢复验证清单

完成恢复动作后，按以下顺序验证：

  • 集中化工单系统登录入口可正常登录。
  • 相关告警已消除或回落到正常阈值。
  • 所有 flow pod readiness 探针全部成功，状态 Ready。
  • 最近日志不再持续出现同类错误关键字。
  • 至少完成一次关键业务路径验证（新建工单/查询/审批）。

根因与预防

根因判断

  • 直接根因：flow 服务假死，pod 启动后服务实例未就绪。
  • 应用表现：用户无法登录集中化工单系统。
  • 处置边界：先恢复健康检查机制和实例就绪，再扩展检查依赖服务和网络。

长期预防

  • 固化 flow 服务存活与就绪探针配置（避免临时改回导致复发）。
  • 补充 flow 服务假死的进程级监控告警（CPU、线程、响应时间）。
  • 建立 pod 就绪超时后的自动重启或告警升级机制。
  • 定期演练多实例同时未就绪的场景，确认故障域可控。
