# 集中化工单系统 - flow服务假死 故障处置手册

> **故障分类**: 应用 | **所属域**: B域 | **首次发生**: 2026-07-09 | **累计次数**: 5次
>
> **最后更新**: 2026-07-09 | **数据来源**: 多域系统故障记录表 + 现场排障
>
> **适用场景**: 集中化工单系统登录异常 / flow 服务假死 / pod 启动后服务实例未就绪
>
> **处置目标**: 确认 flow 服务假死主因，恢复登录与业务入口，固化探针与监控。

关键对象：

## 故障点标注与恢复对象

|| 标注 | 故障点/现象 | 优先恢复动作 | 需要重启/执行的对象 |
||---|---|---|---|
|| 红框 | flow 服务假死，pod 启动后服务实例未就绪 | 修改 pod 健康检查机制（存活/就绪探针） | flow pod（建议逐实例滚动） |
|| 扩展 | 多实例同时未就绪导致用户无法登录 | 检查镜像、配置和启动顺序 | flow 全部 pod、依赖服务 |

## 适用范围与故障判定

### 适用范围

遇到以下任一现象，进入本手册流程处理：

- 集中化工单系统无法登录或登录异常。
- flow 服务假死，进程在但请求无响应或超时。
- pod 启动后服务实例长期未就绪（readiness probe 持续失败）。
- 多实例同时未就绪导致所有用户无法登录。

### 判定规则

|| 如果看到 | 先做什么 | 判断结论 |
||----------|----------|----------|
|| 用户报障无法登录 | 抓取 flow pod 状态与日志 | 收敛到 flow 服务侧 |
|| pod Running 但 readiness 失败 | 检查探针配置和启动依赖 | 服务假活，先恢复探针 |
|| 恢复后仍有登录失败 | 回查页面、接口、日志和监控 | 确认假恢复或依赖未恢复 |

## 标准处置流程

1. 记录故障时间、登录现象、影响入口和受影响实例数。
2. 抓取 flow pod 列表和状态：
   ```bash
   kubectl -n <ns> get pod -l app=flow -o wide
   ```
3. 抓取未就绪实例的就绪探针日志和事件：
   ```bash
   kubectl -n <ns> describe pod <pod>
   kubectl -n <ns> logs <pod> --previous --tail=300
   ```
4. 确认旧实例已隔离或标记不接流量后，修改 pod 健康检查机制（存活/就绪探针），滚动重启。
5. 重启后验证用户登录和集中化工单系统核心入口。
6. 恢复后保留现场（探针配置 diff、pod 事件、关键日志），便于根因回溯。
7. 短时间复发时升级开发定位根因，并补充进程级和就绪级监控。

## 关键检查命令

> 以下命令按本故障场景去重整理；执行前按实际命名空间、标签和权限确认。

### 列出 flow pod 状态

```bash
kubectl -n <ns> get pod -l app=flow -o wide
```

### 查看未就绪 pod 详情

```bash
kubectl -n <ns> describe pod <pod>
```

### 抓取 flow 最近日志

```bash
kubectl -n <ns> logs -l app=flow --tail=300 --since=30m
```

### 查看 readiness/liveness 探针配置

```bash
kubectl -n <ns> get pod <pod> -o jsonpath='{.spec.containers[*].livenessProbe}'
kubectl -n <ns> get pod <pod> -o jsonpath='{.spec.containers[*].readinessProbe}'
```

### 滚动重启 flow

```bash
kubectl -n <ns> rollout restart deployment/flow
kubectl -n <ns> rollout status deployment/flow
```

## 协同分工与通知口径

### 通知口径

> 集中化工单系统出现 flow 服务假死，当前已按手册确认主故障对象为 flow pod 健康检查机制。请对应责任团队优先处理主故障点，运维侧同步保留现场并完成登录、业务入口和监控恢复验证。

### 谁负责什么

|| 角色 | 负责范围 | 处置动作 |
||------|----------|----------|
|| 一线运维 | 告警确认、现场操作、恢复验证 | 执行标准处置流程并记录结果 |
|| 系统维护 / 厂商 | flow 应用、镜像、配置和探针 | 修改健康检查机制并定位反复故障根因 |
|| DBA / 平台支撑 | 依赖服务、数据库、主机和网络 | 在扩展验证异常时介入处理 |

## 恢复验证清单

完成恢复动作后，按以下顺序验证：

1. 集中化工单系统登录入口可正常登录。
2. 相关告警已消除或回落到正常阈值。
3. 所有 flow pod readiness 探针全部成功，状态 Ready。
4. 最近日志不再持续出现同类错误关键字。
5. 至少完成一次关键业务路径验证（新建工单/查询/审批）。

## 根因与预防

### 根因判断

- 直接根因：flow 服务假死，pod 启动后服务实例未就绪。
- 应用表现：用户无法登录集中化工单系统。
- 处置边界：先恢复健康检查机制和实例就绪，再扩展检查依赖服务和网络。

### 长期预防

- 固化 flow 服务存活与就绪探针配置（避免临时改回导致复发）。
- 补充 flow 服务假死的进程级监控告警（CPU、线程、响应时间）。
- 建立 pod 就绪超时后的自动重启或告警升级机制。
- 定期演练多实例同时未就绪的场景，确认故障域可控。
