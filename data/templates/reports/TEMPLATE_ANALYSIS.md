# 故障报告模板结构分析

分析对象：

- `official/XX系统XXXX年XX月XX日故障报告.docx`
- `clean/XX系统XXXX年XX月XX日空白模板故障报告.docx`

本次只做模板复制和结构分析，不开发报告生成逻辑。

## 页面结构

| 项目 | official | clean | 结论 |
| --- | ---: | ---: | --- |
| OOXML parts | 29 | 29 | 一致 |
| section 数 | 1 | 1 | 一致 |
| header 数 | 1 | 1 | 一致 |
| footer 数 | 2 | 2 | 一致 |
| media 图片 | 0 | 0 | 一致，模板不含图片素材 |
| content controls | 0 | 0 | 一致，后续不能依赖 Word 内容控件填充 |
| 非空段落数 | 39 | 14 | official 含示例正文，clean 删除了示例正文 |
| 表格数 | 4 | 4 | 一致 |

页面参数来自 OOXML：

- 页面宽高：`w=11880`, `h=15840`
- 页边距：上 `720`、右 `720`、下 `1080`、左 `720`
- 页眉/页脚距离：`432`
- 装订线：`360`

渲染检查：当前环境缺少 LibreOffice/soffice，`render_docx.py` 无法输出 PNG/PDF，因此本次未完成视觉页图 QA。后续填充逻辑开发前，建议在可打开 Word 或可用 LibreOffice 的环境中再做一次视觉确认。

## 标题层级

两个模板章节标题一致：

1. `XXXX系统X月XX日故障报告`
2. `故障`
3. `故障现象`
4. `影响业务时间信息`
5. `故障发现`
6. `故障处理过程&记录`
7. `故障原因分析&结论`
8. `故障闭环`
9. `后续完善措施`

封面/元信息段落一致：

- `公司:新炬`
- `项目:广东移动`
- `作者:多域维护组`
- `创建日期:2023-5-11`
- `版本:1.0`

## 表格数量与结构

| 表格 | 行列 | 表头 |
| --- | --- | --- |
| 1 | 2 行 x 5 列 | 影响业务、业务故障原因、解决方式、影响业务种类、影响业务范围 |
| 2 | 2 行 x 3 列 | 发生时间、恢复时间、发现人 |
| 3 | 2 行 x 2 列 | 处理时间、处理人 |
| 4 | 2 行 x 4 列 | 故障原因、关闭时间、上报人、上报时间 |

official 第二行含示例值；clean 第二行为空，适合作为填充行。

## 可填充位置

建议后续填充逻辑只填输出副本，不修改模板本体。

| 位置 | 建议来源 |
| --- | --- |
| 标题 `XXXX系统X月XX日故障报告` | `incident_context.incident.system_name` + 日期 |
| 创建日期 | `incident_context.created_at` 或报告日期 |
| 故障现象正文 | `incident_context.incident.fault_description` |
| 表格 1 第 2 行 | 影响业务、业务故障原因、解决方式、影响业务种类、影响业务范围 |
| 表格 2 第 2 行 | 发生时间、恢复时间、发现人 |
| 表格 3 第 2 行 | 处理时间、处理人 |
| 故障处理过程&记录 | `incident_context.incident.process_timeline` |
| 故障原因分析&结论 | `incident_context.incident.fault_cause` + 分析结论 |
| 表格 4 第 2 行 | 故障原因、关闭时间、上报人、上报时间 |
| 后续完善措施 | `incident_context.incident.followup_measures` |

## 格式差异

已确认的结构差异：

- official 含完整示例正文和表格示例值。
- clean 保留同样章节和 4 个表格，但删除了示例正文，表格数据行为空。
- 两者 OOXML parts、section、页眉页脚、样式数量、表格数量一致。
- 两者都没有图片、批注、内容控件。

未确认项：

- 因当前环境缺少 LibreOffice/soffice，未完成渲染页图对比。
- 页面实际视觉效果、分页、页眉页脚呈现需在 Word 或可用 LibreOffice 环境中确认。

## 建议

后续报告生成应采用：

1. `official` 作为唯一正式格式基准，不参与运行时写入。
2. `clean` 作为填充底稿的首选候选，因为结构与 `official` 一致且空白区域更适合写入。
3. 生成时复制 `clean` 到 `outputs/reports/<case_id>/`，只修改输出副本。
4. 如果视觉确认发现 `clean` 与 `official` 有版式差异，则改为复制 `official` 并清除示例内容后填充，但仍只操作输出副本。

当前结论：从 OOXML 结构看，`clean` 可以作为后续填充底稿候选；在完成视觉确认前，不应开始报告填充逻辑开发。
