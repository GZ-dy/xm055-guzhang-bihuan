# 故障闭环 V1 强制规则

本文档是当前项目的 V1 执行规则。Hermes 只作为功能样板，不作为字段、目录、流程或产物结构来源。

## 主数据规则

- `incident_context` 是唯一主数据源。
- 报告、在线记录表、邮件、手册模块只能读取 `incident_context` 和本模块结果。
- 下游产物不得反向补写上游事实。
- 在线记录表字段不得从 Word 报告反推。
- 缺失事实进入 `evidence.missing_fields` 或 `meta.status=need_review`，不得编造默认值。
- 数据库责任边界必须写清：多域维护组负责中间件和服务侧排查，可拨测数据库连通性并通知亚信维护组；数据库侧内容和处置由亚信维护组负责。

## 输入规则

输入可以包括：

- 故障文字描述
- 故障截图
- 日志
- 其他附件

至少需要存在一类输入。附件路径只作为来源引用，不复制到 `outputs/`。

## 模板规则

- `data/templates/reports/official/` 存放唯一正式模板，只读，不允许运行时修改。
- `data/templates/reports/clean/` 存放确认后的干净填充底稿。
- `.workbuddy/报告模板/` 可保留旧流程兼容镜像；若存在旧路径干净模板，报告生成优先读取该镜像，否则读取 `data/templates/reports/clean/`。
- 报告生成时只能复制干净模板到 `outputs/reports/<case_id>/` 后填充。
- 不允许把模板副本放进项目根目录或长期保存在 `outputs/`。
- 不允许自行设计新报告格式。

## 输出规则

正式产物只允许：

- `outputs/reports/<case_id>/<系统><月>月<日>日故障报告.docx`
- `outputs/validation/<case_id>/validation_result.json`
- `outputs/ledger/<case_id>/execution_plan.json`
- `outputs/ledger/<case_id>/record_payload.json`
- `outputs/mail/<case_id>/mail_preview.json`
- `outputs/mail/<case_id>/pre_mail_check.json`
- `outputs/mail/<case_id>/mail_send_result.json`
- `outputs/manuals/<case_id>/manual_match_result.json`

临时产物只允许放在 `work/`：

- `work/cases/<case_id>/incident_context.json`
- `work/intake/`
- `work/tmp/`

历史参考只允许放在 `archive/legacy/`。

## 禁止项

- 禁止恢复 `phase*_outputs`。
- 禁止新增无下游使用的中间 JSON。
- 禁止保留多轮重复 DOCX、重复预览、未定义 gate 文件或临时调试文件。
- 禁止在主流程中引用 `archive/legacy/` 下的代码、脚本、数据或旧路径。
- 禁止在运行时修改 official 模板。
- 禁止从报告解析在线记录表字段。
- 禁止绕过 `--incident-context <path> --apply --confirm-live-write LIVE-WRITE` 执行任何 live 写入。

## 校验和阻断

出现以下情况时，流程必须进入 `need_review` 或失败，不得继续当作已完成闭环：

- `incident_context` 缺少必填字段。
- 时间格式不是 `YYYY-MM-DD HH:mm`。
- `duration_minutes` 不是非负整数。
- 报告 DOCX 未生成或不是 `.docx`。
- 必需 dry-run 产物未生成。
- live 写入缺少 `--incident-context <path> --apply --confirm-live-write LIVE-WRITE`。
- 邮件缺少在线记录表链接但被要求正式发送。
- 手册匹配状态不是已定义枚举。

## 下游模块口径

### 报告

报告只负责把 `incident_context` 填入 Word 模板，输出最终 DOCX。
涉及数据库原因时，报告过程和后续措施不得写成多域维护组处理数据库；应写多域维护组排查中间件和服务、拨测数据库连通性并通知亚信维护组处理数据库侧。

- `事件描述`只写“什么时间、谁反馈了什么故障”，时间显示为`M月D日H点MM分`，不得拼接恢复时间、闭环时长等其他字段。
- `@机器人`、`系统：`等消息路由/字段标签不是故障现象。存在实际时间线且用户未单独填写事件描述或故障标题时，必须从第一条时间节点提取“反馈方 + 真实故障现象”，统一写成“谁反馈了什么故障”；不得把机器人名称、系统标签、故障原因或恢复动作当成故障描述。
- 报告中的处理过程每条只显示 `HH:mm`，不重复显示日期；`incident_context` 内仍保留完整日期时间作为事实来源。
- 用户发送的实际时间节点数量不固定，按`时间1`至`时间N`全部保留；报告、在线表和离线表不得强制补齐、删减、合并或改写成固定 4 条/5 条。每个节点必须包含真实时间和真实处理内容，并按时间顺序排列；缺少恢复验证时继续进入`need_review`，不得补造结束节点。
- 报告中的实际处理时间线应补充`多域维护组`作为运维动作主体；首条在原始报障事实后补充响应和排查动作，中间处置步骤补充主体，末条在业务验证后补充系统运行状态复核，不改写原始事实。
- `后续完善措施`必须结合本次运维处置分点填写，至少覆盖监控告警、处置流程、恢复验证等可执行事项，不写一句笼统结论。
- `后续完善措施`按数据库、中间件、主机、应用/服务四类分别维护多套运维模板，并依据系统、发生时间、故障原因和处置方式稳定选用；同一案件重复生成保持一致，不同案件应避免机械重复同一套话术。

### 在线记录表

在线表 payload 只来自 `incident_context`、报告附件路径、邮件状态和手册状态，不读取 Word 正文。

- 在线表和离线表的`处理人员`必须填写该系统所属小组的实际负责人姓名；优先使用联系人表中的一线 A 角、一线 B 角和二线 A 角，禁止填写`多域维护组`、`基础平台组`等组名。
- 在线表和离线表的`故障描述`必须复用 `incident_context.diagnosis.fault_description`，与报告事件描述保持同一事实来源；不得包含`@机器人`或`系统：`等消息路由/字段标签。
- 离线累计表以 `case_id` 作为唯一幂等键：新 `case_id` 必须紧接最后一条业务记录追加新行，不得按系统或发生时间覆盖历史行；同一 `case_id` 重试才允许更新原行。live 邮件附件必须由更新后的累计主表复制生成，确保包含此前所有新增记录。
- 任何 live 附件上传、记录创建或更新之前，必须先按同系统同发生时间、再按 `case_id` 查重；查重失败或命中不唯一时在外部写入前阻断。命中已有记录时复用其 `record_id` 和已有附件，不得重复上传或新建记录。
- `资料完整度`是派生状态，以飞书记录中有效的`故障报告`和`故障报告附件`为准；两者均存在时必须为`基础资料已齐`。已有非空状态与附件事实矛盾时，允许只纠正该派生字段。
- `多域维护组`只表示处理过程中的操作主体，写入`处理过程`或`处理组`，不得替代`处理人员`。
- 系统、所属域和处理人员以 `data/reference/contacts/multi_domain_contacts.json` 为运行时规则源；该文件已与真实联系人表 `多域系统告警通报联系人-仅姓名版.xlsx` 核对。
- 处理人员固定按“一线 A 角 → 一线 B 角 → 二线 A 角”排序并去空、去重；飞书表和离线表使用同一结果。
- `BI` 在飞书表和离线表中统一写为`经分域`。
- `CLC业务卡`、`CLC业务卡系统`按`业务卡管理系统`匹配；`SmatrBI`按`SmartBI`匹配。
- `大数据K8s`、`大数据K8S`、`大数据平台K8s`、`大数据平台K8S`、`大数据平台K8S集群`的所属域统一写为`经分域`。
- 大数据平台 K8S 没有联系人表依据时，不推断、不编造处理人员；已有明确值`欧阳兹韵`继续保留，直到负责人另行确认。

### 邮件

- 机器人自动发送以飞书 `record_id` 作为幂等键：飞书已标记`已发送`或本地持久状态为`sent`时禁止重复 SMTP；状态为`attempting`或`unknown`时进入人工核验，不得自动重发。人工显式重发不受自动幂等抑制。
- `execution_plan.json` 在查重和附件准备完成后必须刷新，不得用上传前的缺附件状态冒充最终执行计划。

- 主收件人固定为 `gydyjzhwhz@gd.chinamobile.com`。
- 根据所属系统从正式联系人表匹配对应负责人邮箱加入抄送；没有匹配依据时抄送保持为空，不推断、不编造。

邮件正文使用冻结模板：

```text
闭环【xxx系统故障原因。】

一、事件描述： M月D日H点MM分，反馈人反馈xxx故障。
二、业务影响范围： xxx；
三、处理组： xxx
四、故障原因： xxx；
五、解决方案： xxx；
六、故障定界工具： 无；
七、故障发现来源： xxx；
八、业务恢复时长： xx分钟；
```

`故障定界工具` 缺失时固定为 `无`。

### 企业微信机器人

- 收到群消息后立即只回复`收到！`。
- 只有 SMTP 返回`已发送`后才回复`邮件已发送`；失败、阻断或仅生成预览时不得回复发送成功。
- 面向用户的成功回复不附带 `case_id`、报告路径、台账路径或邮件预览路径。

### 手册

手册模块只输出匹配结果和状态。未接入正式手册索引前，默认状态为 `待补充`。

## 迁移到其他电脑

- 上述规则必须跟随工作区代码和便携包交付，不能只存在 Codex/Obsidian 等本机记忆中。
- 便携包必须包含 `src/`、`data/reference/contacts/`、本规则文件、企业微信启动脚本和测试。
- `config/private/feishu.json`、`config/private/wecom_bot.dpapi.json`、SMTP 授权码等机器凭据默认不入包；接收方必须在新电脑重新配置。
